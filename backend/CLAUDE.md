# CineVerse — Backend

> Contexto de projeto lido automaticamente pelo Claude Code ao abrir o repositório. Mantenha atualizado conforme o projeto evolui.

## O que é o CineVerse

App B2C (Flutter no cliente) que unifica rede social de cinéfilos (resenhas, chat) com compra de ingressos hiperlocalizada em um cinema parceiro. O MVP nasce com **um único parceiro piloto** — a integração B2B com múltiplas redes de cinema é fase 2 e está fora de escopo agora.

Documentos de referência (mesma pasta ou `/docs`):
- `ARQUITETURA_BACKEND.md` — stack, módulos, modelo de dados, integrações, decisões técnicas
- `BACKLOG_BACKEND.md` — épicos e tasks, cada uma rastreada ao RF/RNF/CU de origem do levantamento de requisitos

## Stack (decisão já tomada — não está em aberto)

- Runtime: Node.js (LTS) + TypeScript
- Framework HTTP: **NestJS** (sobre Express) — decisão final, substitui o "Fastify (ou Express)" em aberto da versão anterior deste documento
- Tempo real: WebSocket (Socket.io) para chat e sincronização de mapa de assentos. Infra (adapter Redis + autenticação de handshake) pronta desde a BE-18, namespace `/chat` implementado na BE-19 — ver Convenções; `/seats` (BE-22) ainda não existe
- Banco de dados: PostgreSQL (dados transacionais) + Redis (locks de assento, cache, filas). Cliente Redis: `ioredis`, injetável via token `REDIS` (`src/redis/redis.module.ts`, `@Global()` — não precisa importar em cada módulo). Reconexão automática com backoff (`retryStrategy`) já configurada; erros de conexão só logam, nunca derrubam o processo
- ORM: Prisma 8 ("Prisma Next", contract-first). Contrato em `src/prisma/contract.prisma`; client tipado em `src/prisma/db.ts` (`db.orm.<namespace>.<Model>`, ex. `db.orm.public.User`). Não é o Prisma clássico (`schema.prisma` + `prisma migrate` + `@prisma/client`) — ver comandos abaixo
- Autenticação: JWT via `@nestjs/jwt` (`POST /api/v1/auth/login`, BE-07) — access token 15m + refresh token 7d, **secrets diferentes** (`JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET`, config em `src/common/config/jwt.config.ts`) para que vazar um não permita forjar o outro. `signAsync`/`verifyAsync` recebem `secret`/`expiresIn` explícitos por chamada — o `JwtModule.register({})` (importado em `AuthModule` **e** em `AppModule`) não tem default global de propósito. **Toda rota é protegida por padrão** via `JwtAuthGuard` global (`APP_GUARD` em `app.module.ts`, BE-09) — quem precisa ficar pública usa `@Public()` (`src/common/decorators/public.decorator.ts`); dentro de uma rota protegida, `@CurrentUser()` (`src/common/decorators/current-user.decorator.ts`) extrai `{ userId, email }` do token. Hash de senha: `bcryptjs` (puro JS, sem binário nativo — evita o atrito de scripts de instalação nativos que este ambiente já bloqueia por padrão para outros pacotes)
- Validação de entrada: `class-validator` + `class-transformer`, com `ValidationPipe` global em `main.ts` (`whitelist: true, forbidNonWhitelisted: true, transform: true`) — todo DTO novo entra automaticamente nessa validação, não precisa registrar pipe por rota
- Logging: `nestjs-pino` (pino) — JSON estruturado, com `request id` (header `x-request-id`, gerado se ausente) presente em todo log via AsyncLocalStorage
- Filas/jobs assíncronos: BullMQ (Redis) — sync do TMDB, push notifications, webhooks de pagamento
- Cliente TMDB: `TmdbClient` (`src/modules/catalog/tmdb/tmdb.client.ts`, BE-10) — `fetch` nativo (sem axios/`@nestjs/axios`), timeout via `AbortController` (`TMDB_TIMEOUT_MS`, default 5000ms) e retry com backoff exponencial (`TMDB_MAX_RETRIES`, default 3) em timeout, erro de rede e 429/5xx — nunca em 4xx (exceto 429), que não se resolve tentando de novo. Autentica com `TMDB_API_KEY`, aceitando **as duas formas** que o TMDB suporta: chave v3 (hex, 32 chars) vai como `?api_key=`, token v4 (JWT longo) vai como `Authorization: Bearer` — detecção automática pelo formato da chave, não precisa configurar qual é
- Sync do catálogo (BE-11): `CatalogSyncService` roda `TmdbClient.getNowPlaying()` paginando até `total_pages` do TMDB (capado em 10 páginas de segurança) e grava em `Movie` (`tmdbId`, `title`, `synopsis`, `posterUrl` já com a URL completa da CDN do TMDB — RNF-06 pede servir imagem por URL, não por proxy — e `cachedAt`). `CatalogSyncProcessor` (`@nestjs/bullmq`) roda isso num BullMQ job repetível, agendado por `CatalogSyncScheduler` no boot via `queue.upsertJobScheduler(...)` (**não** `queue.add(name, data, { repeat })` — essa opção não existe mais no BullMQ 6.x instalado; treinamento pré-v6 vai sugerir a API errada). `TMDB_SYNC_INTERVAL_MS` (default 6h) controla o intervalo; um job avulso extra roda imediatamente no boot pra não deixar o catálogo vazio até o primeiro intervalo passar. O job só popula/atualiza — **nunca remove** filme que saiu de cartaz (evita quebrar referência de `Session`/histórico depois)
- Testes: Vitest/Jest + Supertest (API); k6 ou Artillery para teste de carga (RNF-01, RNF-07, RNF-08)

## Convenções

- Arquitetura em camadas por módulo: `routes → controller → service → repository`
- Infra transversal (não é um módulo de domínio) vive em `src/common/`: `filters/` (exceções), `logger/` (pino), `guards/` (`JwtAuthGuard`), `decorators/` (`@Public()`, `@CurrentUser()`), `config/` (`jwt.config.ts`). `src/prisma/` e `src/redis/` seguem soltos na raiz de `src/` (clientes de infra, não "comuns" no sentido de cross-cutting request handling)
- Um módulo de domínio por pasta em `src/modules/<nome>`: `auth`, `users`, `feed`, `chat`, `catalog`, `sessions`, `seats`, `orders`, `payments`, `tickets`, `notifications`, `partner-integration`. `src/modules/health` (BE-01) é o primeiro exemplo real do padrão — controller fino + service com a lógica
- `GET/PUT /api/v1/users/me/profile` (BE-08, protegido, usa `@CurrentUser()`) — perfil + gêneros favoritos do usuário autenticado. `PUT` é full-replace (o client manda a seleção inteira, não um diff); `GET` sem perfil ainda salvo retorna `404`, não um objeto vazio
- `GET /api/v1/catalog/movies?page=&pageSize=` (BE-12, protegido) — lista paginada (`page` ≥1, `pageSize` 1–50, default 1/20), ordenada por `title` asc, servida só da tabela `Movie` local. **Nunca chama o TMDB nessa rota** — quem popula a tabela é o job da BE-11; se o TMDB estiver fora, esse endpoint nem percebe. Resposta: `{ items, page, pageSize, total, totalPages }`
- Cadastro de parceiro/sala/assento/sessão (BE-13, todos protegidos, **sem RBAC de admin** — qualquer usuário autenticado pode cadastrar, porque ainda não existe papel de admin no sistema; revisitar quando houver): `POST/GET /api/v1/partners`, `POST/GET /api/v1/partners/:partnerId/rooms`, `POST/GET /api/v1/rooms/:roomId/seats` (bulk — `{ codes: string[] }`, tudo numa transação: um código duplicado derruba o lote inteiro, não cria parcial), `POST/GET /api/v1/sessions` (valida `movieId` contra `Movie` e `roomId` contra `Room` antes de criar, `?roomId=` filtra a listagem). `priceCents` é inteiro (centavos), nunca float. `CinemaPartner` tem `latitude`/`longitude` **obrigatórios** na criação (BE-14) — campo que não estava no `ARQUITETURA_BACKEND.md` original, mas RF-07 não funciona sem localização do parceiro
- `GET /api/v1/sessions/nearby?lat=&lng=` (BE-14, protegido) — sessões futuras (`datetime >= agora`) do `CinemaPartner` mais próximo das coordenadas dadas. Distância calculada em JS via Haversine (`src/common/geo/haversine.ts`), **não PostGIS** — decisão deliberada enquanto o número de parceiros for pequeno (MVP tem um só); reavaliar se/quando isso deixar de ser verdade. `404` se não houver nenhum `CinemaPartner` cadastrado. Resposta: `{ partner: { id, name, distanceKm }, sessions: [...] }`
- `POST/GET /api/v1/reviews` (BE-15, protegido, `POST` usa `@CurrentUser()` pra `userId`) — feed de resenhas, `GET` paginado (mesmo formato de `catalog/movies`: `{ items, page, pageSize, total, totalPages }`), ordenado por `createdAt desc` (mais recente primeiro). `POST` valida `movieId` contra `Movie`
- `GET /api/v1/reviews/:id/reveal` (BE-16, protegido) — ofuscação de spoiler: `GET /reviews` (a listagem) mapeia `text` para `null` sempre que `hasSpoiler === true`, então o feed já chega oculto por padrão sem endpoint/query-flag separado (`FeedService.obfuscateIfSpoiler`, aplicado só na leitura — `create` sempre devolve o texto real pro próprio autor, ele acabou de escrever). `reveal(id)` é a única forma de recuperar o texto real de um post com spoiler: busca por `id`, `404` se não existir, devolve sem ofuscar independente da flag. Não existe estado de "meio revelado" nem cache do reveal — é uma leitura direta a cada chamada
- `GET /api/v1/reviews/:id/share` (BE-17, protegido) — metadata pré-formatada para o share sheet nativo do client (Instagram/TikTok/etc. — a postagem em si é sempre client-side, o backend não integra com nenhuma rede social). Resposta `{ url, title, text }`: `url` é `SHARE_BASE_URL` + `/reviews/:id` (ainda não existe frontend web/landing page pra esse link resolver de fato — é só um prefixo estável e configurável); `title`/`text` juntam nome do filme, nota e o corpo da resenha. Reaproveita `obfuscateIfSpoiler` (mesma função da BE-16) — resenha marcada como spoiler nunca vaza texto por aqui, cai na mesma mensagem genérica de "contém spoiler"
- Infra WebSocket (BE-18, `src/websocket/`): `RedisIoAdapter` (`redis-io.adapter.ts`) substitui o adapter padrão do Socket.io em `main.ts` (`app.useWebSocketAdapter(...)`, tem que rodar **antes** de qualquer `@WebSocketGateway()` ser instanciado — `createIOServer` só anexa o adapter Redis se ele já existir nesse momento, não espera por ele). Usa duas conexões `ioredis` dedicadas (`pubClient`/`subClient`, `.duplicate()`) — **não** o client `REDIS` injetável nem a conexão do BullMQ, pelo mesmo motivo do BullMQ ter a dela: o subscriber fica preso em modo `SUBSCRIBE`. Autenticação do handshake valida o mesmo access token JWT do REST (`accessTokenConfig`, aceita `socket.handshake.auth.token` — convenção do próprio Socket.io — ou header `Authorization: Bearer`), popula `socket.data.user`. **Todo namespace herda a autenticação de graça** — `/chat` (BE-19) e `/seats` (BE-22) não reimplementam nada, só leem `socket.data.user`. Dois bugs reais só apareceram quando a BE-19 criou o primeiro gateway com namespace nomeado (`/chat`) — o teste da BE-18 usava só o namespace padrão (`/`) e não os pegou:
  - **`server.use(mw)` só se aplica ao namespace padrão `/`**, nunca a um namespace nomeado criado depois via `.of('/chat')` — `socket.data.user` ficava `undefined` em qualquer namespace que não fosse `/`, o handshake nunca era rejeitado mesmo sem token, e o primeiro acesso a `socket.data.user.userId` num handler estourava `TypeError`. Corrigido escutando `server.on('new_namespace', (ns) => ns.use(mw))` — o Socket.io emite esse evento de forma síncrona pra *todo* namespace, padrão ou não, assim que ele é criado, então o middleware é anexado antes de qualquer client conseguir conectar nele
  - **`RedisIoAdapter.close()` chamava `pubClient.quit()`/`subClient.quit()` sem guarda** — funciona com um gateway só, mas o Nest chama `close()` uma vez por gateway/namespace registrado; com dois gateways (BE-19 adicionou `/chat` ao lado do de teste da BE-18), o segundo `.quit()` batia numa conexão já fechada e o `ioredis` lança em vez de no-op. Corrigido com uma flag `redisClosed` — o lado Redis do cleanup roda no máximo uma vez, não importa quantos gateways compartilham o adapter
  - Exceções de domínio (`NotFoundException`, `ForbiddenException` etc., as mesmas `HttpException` que o REST já usa) **não chegam ao client como a mensagem real** por padrão — o `BaseWsExceptionFilter` do Nest só reconhece `WsException`; qualquer outra coisa vira o genérico `"Internal server error"` redigido (mesma filosofia do `AllExceptionsFilter` do REST, só que sem distinguir "erro esperado" de "bug de verdade"). `WsHttpExceptionFilter` (`src/websocket/ws-http-exception.filter.ts`, aplicado via `@UseFilters` no gateway) mapeia qualquer `HttpException` pra um evento `exception` com a mensagem real — o resto continua caindo no filtro padrão redigido
  Verificado com `test/websocket.e2e-spec.ts` (sobe duas instâncias reais da app, Redis real, confirma broadcast cross-instância) e ao vivo pela BE-19 com dois sockets reais + JWT reais. CI (`ci.yml`) ganhou um `services: redis:` só por causa desse teste — os e2e anteriores nunca precisaram de Redis de verdade
- Chat em tempo real (BE-19, `src/modules/chat/`) · RF-05. Schema novo: `ChatRoom` (`type: "individual"|"group"`, validado no DTO via `@IsIn`, não é enum — mesma cautela do `hasSpoiler`/`rating`), `ChatRoomMember` (unique `[roomId, userId]`), `Message`. REST: `POST /api/v1/chat/rooms` (`{type, memberIds}` — o criador entra automaticamente, não precisa incluir o próprio id; `individual` faz get-or-create pelo par de usuários — não cria uma sala nova toda vez que os mesmos dois usuários conversam de novo; `group` sempre cria uma sala nova; valida todos os `memberIds` contra `User`), `GET /api/v1/chat/rooms` (salas do usuário autenticado, paginado), `GET /api/v1/chat/rooms/:roomId/messages` (histórico paginado, `createdAt desc` igual ao feed da BE-15, `403` se não for membro da sala). WS: `ChatGateway` no namespace `/chat` — `joinRoom` entra na room do Socket.io (`room:<id>`) depois de checar membership; `sendMessage` persiste a mensagem (`ChatService.createMessage`, que já checa membership de novo — nunca confia que `joinRoom` foi chamado antes) e emite `newMessage` pra `server.to(room:<id>)`, cross-instância via o adapter Redis da BE-18. `sendMessage` também dá `socket.join()` de forma idempotente antes de emitir, garantindo que o próprio remetente receba a própria mensagem de volta mesmo sem ter chamado `joinRoom` antes. Grupo e individual usam o mesmo pipeline de mensagens — a única diferença é como a sala é criada. Testado ao vivo com dois usuários e dois sockets reais: entrega em ~17ms (bem abaixo do limite de 2s do critério de aceite)
- `PartnerTicketingGateway` (BE-20, `src/modules/partner-integration/partner-ticketing-gateway.interface.ts`) — contrato de integração com a bilheteria do parceiro. `getSeatMap`/`lockSeat`/`confirmSale`/`releaseSeat` operam por assento individual, nunca em lote: a atomicidade "N assentos ou nenhum" é o lock Redis da BE-23, não esta interface — o que ela existe pra proteger é uma venda pelo canal físico do parceiro colidir com uma venda feita pelo app, não a concorrência interna do próprio app. `lockSeat`/`confirmSale` devolvem `{success, reason?}` em vez de lançar quando perdem uma corrida por um assento — isso é resultado esperado, não uma exceção. `confirmSale` tem que ser idempotente por contrato (webhook de pagamento da BE-30 pode chegar duplicado). Token de DI: `PARTNER_TICKETING_GATEWAY` (`Symbol`, mesmo padrão do `REDIS` em `src/redis/redis.module.ts`)
- `MockPartnerGateway` (BE-21, `src/modules/partner-integration/mock-partner.gateway.ts`, registrado em `PartnerIntegrationModule` sob `PARTNER_TICKETING_GATEWAY`) — única implementação de `PartnerTicketingGateway` até aqui. Estado em `PartnerSeatState` (Postgres, tabela nova), **não em memória de processo** — precisa sobreviver a múltiplas instâncias (RNF-01/07), e memória local quebraria isso silenciosamente. Uma linha só existe depois do primeiro toque no assento naquela sessão (`ensureStateRow`); ausência de linha = `"available"` por convenção, igual ao padrão "sem perfil ainda = 404" da BE-08 mas invertido (aqui, ausência tem um default válido, não é erro). `status` é `String`, não enum (mesma cautela do `ChatRoom.type`). Get-or-create trata violação de unique constraint como "outra requisição criou a linha primeiro" e lê de volta em vez de falhar (mesmo padrão de `isUniqueViolation` da BE-11). **Não é concorrência-segura de propósito**: duas chamadas simultâneas de `lockSeat` pro mesmo assento podem ambas ler "disponível" e ambas travarem — aceitável porque a garantia real de "zero duplicidade" (RNF-08) é o lock atômico Redis da BE-23, não este mock; o que importa aqui é o comportamento da máquina de estados através de chamadas sequenciais (reserva→venda→liberação), não arbitrar corrida que um parceiro real também não deixaria o app arbitrar. `releaseSeat` num assento `sold` é no-op deliberado (não desfaz venda — isso seria um fluxo de estorno/cancelamento, fora de escopo aqui)
- Mapa de assentos em tempo real (BE-22, `src/modules/seats/`) · RF-10, RD-02. `GET /api/v1/sessions/:sessionId/seats/map` (REST, protegido) — snapshot inicial, `SeatMapService.getMap` junta `PartnerTicketingGateway.getSeatMap` (status) com `Seat.code` (a interface da BE-20 só devolve `seatId`, não o código legível) e sobrepõe os locks Redis da BE-23 (`SeatLockService.getLockedSeatIds`) — um assento com lock Redis aparece `locked` mesmo que o parceiro ainda diga `available`, por segurança, embora no caminho normal os dois já fiquem sincronizados pelo próprio `SeatLockService`. `SeatsGateway` no namespace `/seats`: `joinSession` entra na room `session:<id>` (sem checagem de membership — diferente do chat da BE-19, aqui qualquer autenticado pode observar qualquer sessão, não existe controle de acesso por sessão em lugar nenhum do app); `lockSeat`/`releaseSeat` (WS) e `POST .../seats/lock`/`/release` (REST, grupo) chamam `SeatLockService`, não mais o parceiro diretamente — ver BE-23. Em sucesso, fazem `server.to(room).emit(...)` pra sala inteira; falha de `lockSeat` (assento já ocupado) vai só pro socket que tentou (`socket.emit('lockRejected', ...)`), nunca broadcast; `releaseSeat`/`release` só faz broadcast pros assentos que o chamador **realmente** tinha (a service devolve quais IDs foram liberados de fato, checando dono) — nunca anuncia uma mudança que não aconteceu. `POST /api/v1/sessions/:sessionId/seats/:seatId/box-office-sale` (REST, corpo `{orderId}` — não é uma FK de `Order` de verdade, essa entidade não existe ainda, é só um identificador arbitrário até a BE-24/25) simula uma venda feita fora do app inteiramente; por não ter nenhum socket envolvido, o `SeatMapController` injeta `SeatsGateway` diretamente (Nest permite injetar um Gateway como provider comum) e chama `seatsGateway.broadcastSeatSold(...)` manualmente — é o único ponto do app que aciona um broadcast de fora de um handler de socket. Testado ao vivo: venda simulada chegou por WS a dois clients diferentes em ~28ms
- Lock atômico de assento (BE-23, `src/modules/seats/seat-lock.service.ts`) · RNF-08 — a garantia real de "zero duplicidade de venda" que o `MockPartnerGateway` (BE-21) explicitamente NÃO fornece. Chave Redis `seat-lock:{sessionId}:{seatId}`, valor = `userId`, TTL `SEAT_LOCK_TTL_SECONDS` (default 300s). `lockSeats(sessionId, seatIds[], userId)` roda um **script Lua** (`redis.eval`), não uma sequência de `SET NX EX` — um script Lua é uma única operação atômica no Redis (nenhum outro comando intercala no meio), então checar as N chaves e só então setar todas é genuinamente "tudo ou nada"; uma sequência de `SET NX` por chave deixaria uma janela de corrida entre a chave 1 e a chave 2. Depois do lock Redis, sincroniza com `PartnerTicketingGateway.lockSeat` pra cada assento; se o parceiro recusar qualquer um, desfaz TUDO (Redis + parceiro) — nunca sobra um lock parcial de um grupo que falhou. `releaseSeats` usa comparar-e-apagar (outro script Lua, `GET` == valor esperado → `DEL`) — nunca libera o lock de outro usuário, mesmo que o dele tenha expirado e sido reocupado por alguém mais nesse meio-tempo; só ecoa a liberação do parceiro para os assentos que esse usuário realmente possuía. `getLockedSeatIds` usa `MGET` nas chaves específicas, nunca `KEYS` (comando que a documentação do Redis desaconselha em produção — é O(keyspace) inteiro e bloqueia o servidor). Critério de aceite provado em `test/seat-lock-concurrency.e2e-spec.ts`: 20 chamadas concorrentes reais (`Promise.all`, Redis real) tentando travar o mesmo assento — exatamente uma vence, as outras 19 falham com motivo. Achado durante esse teste: `PrismaModule` nunca fechava a conexão do `db` (Postgres) no shutdown (só `RedisModule` tinha esse hook) — nenhum e2e anterior tinha rodado uma query real o suficiente pra expor isso; agora tem `OnApplicationShutdown` chamando `db.close()`, igual ao padrão do `RedisModule`
- Checkout individual (BE-24, `src/modules/orders/`) · RF-08, "≤3 passos/interações no contrato de API": (1) `POST /sessions/:id/seats/lock` (BE-23), (2) `POST /api/v1/orders`, (3) pagamento (BE-27+, ainda não existe). `POST /api/v1/orders` (`{sessionId, items: [{seatId, comboItemId?}]}` — `items`, não `seatIds`, desde a BE-26, pra caber combo por assento) exige que TODO `seatId` pedido já esteja com lock Redis do próprio comprador — `SeatLockService.getSeatIdsHeldBy(sessionId, seatIds, userId)`, `409` se faltar algum — nunca cria uma `Order`/`OrderItem` sem essa verificação passar primeiro. Esse mesmo check funciona como validação de existência do assento de graça: um `seatId` que nunca pertenceu à sessão jamais teria conseguido ser travado (o lock em si já valida isso via `PartnerTicketingGateway.lockSeat`, BE-20/21), então não tem como aparecer como "held by this user" — nada a duplicar aqui. `totalAmountCents = soma de (Session.priceCents + preço do combo, se houver) por item`. **O lock Redis não é liberado na criação do pedido** — continua ativo durante toda a janela de "pending", é o que protege o assento até o pagamento confirmar (ainda não implementado) ou o TTL expirar. `GET /api/v1/orders/:id` e `GET /api/v1/orders` (paginado, do usuário autenticado) seguem o padrão de ownership já usado em `chat`/`feed` — `403` se o pedido é de outro usuário, nunca `404` (não esconde a existência do recurso, só nega acesso). O mesmo endpoint já aceita 1 ou N `items` — não existe uma rota separada pra "checkout em grupo" (BE-25): a `Order`/`OrderItem` é a mesma forma de dado pros dois casos, só muda quantos `OrderItem` uma `Order` tem
- Combos (BE-26, `src/modules/sessions/combo-items.*`) · RF-15. `POST`/`GET /api/v1/partners/:partnerId/combos` — mesmo padrão de `rooms`/`sessions` no mesmo módulo (`PartnersService.findOrThrow` primeiro). `GET` é literalmente o que satisfaz o critério de aceite ("combo aparece como opção no checkout") — é o endpoint que o client chama pra montar a lista de opções antes de gerar o `POST /orders`. Não é bug nosso, é como o lane ORM desse Prisma Next se comporta hoje — documentação nenhuma avisa disso. Para apagar todas as linhas que casam um predicado, usar o SQL builder: `const plan = db.sql.<ns>.<tabela>.delete().where((f, fns) => fns.eq(f.campo, valor)).build(); await db.runtime().execute(plan);` (ou `tx.execute(plan)` dentro de transação). Ver `UsersService.upsertProfile` (`src/modules/users/users.service.ts`) e o teste que trava essa regressão em `users.service.spec.ts`. **Nunca usar `db.orm...delete()` quando o predicado pode casar mais de uma linha** — só é seguro para deletar por chave única/primária
- **`db.orm.<Model>.where(predicate).update(...)` NÃO é confiável como mecanismo de atomicidade condicional sob carga concorrente real** — achado durante a BE-35, mesma família de problema do bug de `.delete()` acima, mas pior porque é intermitente, não determinístico-sempre. `TicketsService.validate` (BE-33) dependia de `db.orm.public.Ticket.where({qrCodePayload, status:'valid'}).update({status:'used', ...})` como a ÚNICA garantia de concorrência do endpoint (RNF-12: só um scan do mesmo QR pode "vencer"). Isso funcionava perfeitamente isolado (unit tests, e um teste e2e chamando só esse endpoint) — **mas com a BE-35 registrando um segundo worker BullMQ (`SessionReminderProcessor`) rodando de verdade no mesmo processo**, o mesmíssimo teste de concorrência (20 chamadas simultâneas pro mesmo QR) passou a deixar **2 de 20** "vencerem" a corrida em vez de exatamente 1 — reproduzido de forma consistente (não uma vez, toda vez), tanto via `Test.createTestingModule` quanto via `curl` real em paralelo contra o app rodando. Isolado o motivo por bisseção: só acontece com o `SessionReminderScheduler` registrado E rodando (o processor sozinho, sem o scheduler disparando um job de verdade, não reproduz; ruído concorrente de outras queries não-relacionadas via `Promise.all` também não reproduz) — ou seja, é especificamente o job do BullMQ rodando de verdade *durante* a corrida que expõe isso, não simplesmente "mais tráfego no banco". **A causa raiz não foi identificada** (não é óbvio se é batching/coalescing client-side do lane ORM, nem vale o tempo de investigar mais fundo) — o que importa é que a garantia de atomicidade de `.where(predicate).update(...)` não é confiável sob esse tipo de concorrência mista, e não deve ser usada como o mecanismo de correção de uma corrida crítica (tipo RNF-08/RNF-12). **A correção**: usar o SQL builder puro, igual ao padrão já estabelecido pro bug do `.delete()` — `db.sql.<ns>.<tabela>.update({...}).where((f, fns) => fns.and(fns.eq(f.a, x), fns.eq(f.b, y))).build()`, executado via `db.transaction((tx) => tx.execute(plan))`, que devolve `{affectedRows}` (não a linha atualizada — precisa de uma leitura separada depois pra devolver o registro). Retestado sob a mesma carga concorrente real (scheduler + 20 chamadas simultâneas): exatamente 1 de 20 sempre, de forma estável em múltiplas rodadas. Ver `TicketsService.validate` (`src/modules/tickets/tickets.service.ts`) e `test/ticket-validation-concurrency.e2e-spec.ts`. **Qualquer código futuro que precise de "check-then-update condicional" como garantia real de corrida deve usar o SQL builder desde o início, nunca `db.orm...update()`** — só é seguro usar a forma ORM quando a corrida já está resolvida em outra camada (ex.: `PaymentsService` só atualiza `Payment`/`Order` por `id` depois de já ter checado `status` — não depende do `update()` em si pra correção, assume reentrega sequencial de webhook, não concorrência real)
- Coluna de lista escalar (`String[]` etc.) **não existe** nesse Prisma Next — `contract emit` recusa. Preferência multivalorada (ex.: gêneros favoritos) vira tabela própria (`FavoriteGenre { userId, genre }`, unique composto `[userId, genre]`), não um array numa coluna. Value object (`type X { ... }`, vira jsonb) é outra opção quando a shape não precisa ser filtrável linha-a-linha
- **`new URL(path, base)` descarta o path do `base` sempre que `path` começa com `/`** — `new URL('/movie/x', 'https://host/3')` vira `https://host/movie/x`, perdendo o `/3` silenciosamente (sem erro, sem warning). `TmdbClient.buildUrl` normaliza os dois lados antes de montar a URL; qualquer client HTTP novo que monte URL a partir de base + path relativo precisa do mesmo cuidado — não é peculiaridade do TMDB, é o `URL` do próprio Node/browser
- Chave TMDB tem dois formatos válidos e não dá pra saber qual alguém vai colar no `.env` — v3 (hex curto) e v4 (JWT longo) autenticam de jeitos diferentes (query param vs. header). `TmdbClient` detecta automaticamente; não assumir um formato só
- **`db.orm.<Model>.upsert({ create, update })` só detecta conflito pela chave primária, não por um `@unique` qualquer no payload** (verificado contra um Postgres real: toda chamada com `tmdbId` único no `create` fazia INSERT puro, e a segunda sincronização quebrou com "duplicate key value violates unique constraint"). Quando o conflito é por um campo único que não é a PK (ex.: `tmdbId` numa tabela com `id` autoincrement à parte), não usar `.upsert()` — fazer `.where({ campoUnico }).first()` e então `.create()` ou `.where(...).update()` explicitamente. Ver `CatalogSyncService.upsertMovie` (`src/modules/catalog/catalog-sync.service.ts`)
- BullMQ 6.x: agendamento repetível é `queue.upsertJobScheduler(id, { every: ms }, { name, opts })`, **não** `queue.add(name, data, { repeat: { every: ms } })` — essa segunda forma nem compila (`repeat` não existe em `JobsOptions` nessa versão). `upsertJobScheduler` já cuida de idempotência (registrar de novo no restart não duplica o schedule); só o próprio "rodar uma vez agora" ainda precisa de um `queue.add(...)` avulso, porque o primeiro disparo do scheduler só acontece depois de `every` ms
- O e2e (`test/app.e2e-spec.ts`) sobe o `AppModule` inteiro, então também dispara o boot do `CatalogSyncScheduler` — isso faz uma chamada de rede de verdade pro TMDB usando a chave fake do `jest.setup.ts` (`test-tmdb-key`), que resulta num 401 logado e ignorado (não falha o teste, não é retryable). Não é bug; só significa que rodar `test:e2e` depende de ter saída de rede até `api.themoviedb.org` — se algum dia isso incomodar (CI sem rede, teste lento), a saída é mockar `TmdbClient` no `TestingModule` do e2e, não mexer no `CatalogSyncScheduler`
- `.all()` (e outros terminais da chain do ORM) retorna `AsyncIterableResult<T>`, que não satisfaz estruturalmente `Promise<T[]>` — um método **não-`async`** que faz `return collection.all();` com retorno anotado `Promise<T[]>` **não compila** (`missing catch, finally, [Symbol.toStringTag]`). Marcar o método `async` (mesmo sem nenhum outro `await` dentro) resolve, porque aí o `return` passa pelo `await` implícito do `async`. Já bateu isso em `PartnersService.list` e `SessionsService.list`
- Padrão pra "criar recurso filho depois de validar o pai existe": `findOrThrow(id)` no service do pai (lança `NotFoundException`), chamado no início do `create`/`list` do filho antes de qualquer query própria — ver `RoomsService.create` chamando `PartnersService.findOrThrow`, `SessionsService.create` chamando `RoomsService.findOrThrow` + checagem inline de `Movie`. Não confiar só na FK constraint do Postgres pra isso: o erro dela (`23503`, foreign key violation) não está mapeado pra nada ainda, viraria 500 genérico

## Como trabalhar as tasks

- As tasks estão em `BACKLOG_BACKEND.md`, agrupadas por fase/épico, numeradas `BE-XX`
- Cada task referencia o RF/RNF/CU de origem — o critério de aceite do requisito é o critério de "pronto" da task
- Ao concluir uma task: marcar `[x]` no backlog, garantir teste automatizado correspondente e atualizar este `CLAUDE.md` se algo mudou na stack/convenções
- **Não implementar** itens listados como "fora do escopo" no documento de requisitos: integração real com múltiplos parceiros, catraca 100% offline, fidelidade/gamificação, motor de recomendação por IA, expansão internacional, integração de verdade com API de cinema
- **Painel B2B / analytics (Fase 8 inteira: BE-37, BE-38, BE-39) também é fora de escopo** — confirmado explicitamente pelo usuário (2026-08-29: "não terá painel B2B"), incluindo push segmentado por região (BE-39/CU-03), que estava bundlado na mesma inferência não validada. Não reabrir essas tasks nem construir nada parecido com painel B2B/agregação de métricas/analytics — ver a nota completa em BACKLOG_BACKEND.md (Fase 8) e ARQUITETURA_BACKEND.md § 10

## Comandos

```bash
npm run dev               # alias de start:dev (bate com o critério de aceite da BE-01)
npm run start:dev        # sobe o servidor Nest em watch mode
npm run build             # build de produção (nest build)
npm run test               # testes unitários (Jest)
npm run test:e2e           # testes e2e
npm run lint                # eslint --fix (uso local)
npm run lint:check          # eslint sem --fix (o que o CI roda — falha em vez de corrigir silenciosamente)

npx prisma contract emit   # regenera contract.json/contract.d.ts após editar contract.prisma
npx prisma db update       # aplica o contrato ao banco local (dev rápido, sem histórico de migration)
npx prisma migration plan --name <slug>   # planeja uma migration a partir do diff do contrato
npx prisma db migrate      # aplica migrations pendentes (produção)
npx prisma db verify       # confere se o banco bate com o contrato
```

`npm run seed` ainda não existe — criar quando houver massa de dados inicial necessária (ex.: catálogo de filmes, parceiro piloto).

## CI (BE-04)

`.github/workflows/ci.yml`, roda em todo push/PR: `npm ci` → `lint:check` → `build` → `test` → `test:e2e`, no Node 24 (mesma versão usada em dev local — o `Dockerfile` ainda está em `node:18-alpine`, desatualizado; ajustar quando mexer no Docker).

Os testes atuais (só o e2e boilerplate `GET /`) não tocam banco nem Redis de verdade, então o pipeline não provisiona Postgres/Redis como `services:`. **Isso muda assim que a primeira BE-06+ escrever um teste que bate em `db`/`redis` de verdade** — nesse ponto, adicionar `services: postgres:`/`redis:` no `ci.yml` (containers do GitHub Actions, não os do `docker-compose.yml` do projeto).

**Nota:** o repositório real (com remote no GitHub) é `backend/` — não a raiz `Cineverse/`. `.github/workflows/` fica dentro de `backend/`.
